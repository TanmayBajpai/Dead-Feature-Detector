Section 1

The Problem

Large C/C++ projects — think LLVM, CPython, Linux — accumulate feature flags over years. A feature flag is a #define preprocessor macro or a runtime boolean like g_feature_enabled that gates a chunk of code:

// Example: compile-time flag
#ifdef ENABLE_LEGACY_PARSER
void old_parse() { /* 300 lines of old code */ }
#endif

// Example: runtime flag
static int g_feature_zlib = 0;   // never set to 1 in any build
if (g_feature_zlib) {
    compress_with_zlib(data);    // dead — never executes
}

The trouble is: some flags are never actually enabled in any real build, yet the code stays in the codebase indefinitely. Nobody knows it's dead. Standard compiler optimisations remove dead code within a single file, but they cannot tell you which feature-flag combinations are unused across all builds of a large project.

⚠️ The Gap in Existing Tools

Dead-code eliminators (DCE) only work per-file, per-compilation. They cannot cross-reference the build system to know which #define combinations are actually used across all targets.

✅ What This Tool Does

Combines build-system analysis (which #define sets exist) with IR-level reachability (is this code block ever reached?) to find code dead across all configurations.

Two things no existing tool combines

  1. Build-system configuration analysis — which #define sets are actually used across all real build targets (from CMake or Makefiles)
  2. IR-level reachability — which code regions are unreachable in the compiled program regardless of input
Key insight: A feature can be "dead" in two ways. Either the preprocessor strips it before the compiler ever sees it (compile-time dead), or the code is compiled in but a runtime flag is always zero so the branch never executes (runtime dead). A third case is when a function exists but nobody in the whole program ever calls it (interprocedural dead).

Section 3 · Component 1

Build Configuration Extractor

What it does: Reads the project's build system to discover every #define that gets passed to the compiler for every build target. Outputs a JSON manifest.

What is a "build configuration"?

When you compile a C/C++ project, the build system (CMake or Make) passes flags to the compiler like -DENABLE_ZLIB=1 or -DNDEBUG. Different build targets (e.g. Debug vs Release, different platforms) get different sets of flags. The extractor enumerates all of these.

Three Parsing Strategies (in priority order)

🏆 1. CMake File API Preferred

CMake's built-in JSON output. Run cmake -S . -B build and CMake writes machine-readable JSON to build/.cmake/api/v1/reply/. Parsed by cmake_api.py. Most accurate — directly from CMake's internal model.

🔄 2. compile_commands.json Fallback 1

A standard JSON file most C++ build systems can generate (-DCMAKE_EXPORT_COMPILE_COMMANDS=ON). Lists every compiler invocation. The extractor greps for -D flags in each command.

🔧 3. Makefile Dry-Run Fallback 2

For Makefile projects: run make -np --dry-run which prints all commands without executing them. Parse compiler lines for -D flags. Works on projects that don't use CMake.

Output Format

{

    {
      "name": "clangBasic",
      "compile_definitions": ["LLVM_ENABLE_THREADS=1", "NDEBUG"],
      "source_files": ["lib/Basic/Foo.cpp", "lib/Basic/Bar.cpp"]

Section 4 · Component 2

LLVM IR Analyzer (The Core)

This is the heart of the tool. It is written in C++17 using the LLVM API and compiled into a shared library (DeadFeaturePass.so) that plugs into LLVM's opt tool.

What is LLVM IR?

When Clang compiles a C/C++ source file, it first converts the source code to LLVM Intermediate Representation (IR) — a platform-independent, typed assembly-like language. IR is stored in bitcode (.bc) files. The tool analyses the IR, not the raw source.

Why analyse IR and not source? Source files are hard to analyse correctly (macros, includes, preprocessor state). IR is already fully resolved — the compiler has done the hard parsing. IR also carries DWARF debug metadata that links every instruction back to its original source file and line number.

What is an LLVM Pass?

An LLVM pass is a visitor that walks the IR and collects or transforms information. This tool implements a ModulePass — it receives the entire linked program (all functions, all globals) in one shot and runs three detection phases over it.

// How the pass is invoked by opt:
opt --load-pass-plugin=./DeadFeaturePass.so \
    -passes=dead-feature \
    --dead-feature-output=ir_findings.json \
    program.bc -o /dev/null

Why -O0 Bitcode?

The tool requires bitcode compiled at -O0 (no optimisations). At -O1 and above, the compiler's own simplifycfg pass deletes unreachable blocks before our pass can see them — so we'd get zero findings. At -O0, dead blocks are preserved literally as written in source.

❌ At -O1 or higher

Compiler's own dead-code passes delete unreachable blocks first. Our pass sees a cleaned-up IR with no dead blocks to report.

✅ At -O0 (required)

All blocks, including dead ones, are preserved. Our pass can find and report them, giving developers the information to remove them manually.

Bitcode Generation Command

clang -O0 -gline-tables-only -fno-discard-value-names \
      -emit-llvm -c source.cpp -o source.bc

llvm-link source1.bc source2.bc -o program.bc   # whole-program link

The flags mean: -O0 no optimisations, -gline-tables-only emit DWARF line numbers (so we can map back to source), -fno-discard-value-names keep basic block names readable, -emit-llvm output bitcode not machine code.

Section 4 (continued) · Detection Phases

Three Detection Phases

All three phases run in a single pass over the module. Each produces findings with a different confidence score.

Phase 1 — Compile-Time Dead Blocks confidence 0.95

What it finds: Basic blocks with no predecessors in the Control Flow Graph (CFG) — code that is unreachable by any path through the function.

How it works

A basic block is compile-time dead if all three conditions hold:

  1. It is not the entry block of the function
  2. pred_empty(&BB) — no other block has an edge pointing to it
  3. !BB.hasAddressTaken() — not referenced via a computed-goto pointer
// Typical source that creates
// a compile-time dead block:
void foo() {
  return;
  // ↓ This block has no
  // predecessors in the CFG
  do_something_dead();
}
Why 0.95 and not 1.0? There is a tiny 5% gap to account for edge cases where DWARF debug info attributes a block to a different file than expected, or where blockaddress usage is present but not detected.

Phase 2 — Runtime Dead Blocks confidence 0.85

What it finds: Conditional branches where one side is provably never taken because a feature-flag global is always zero.

Step 1: Identify feature-flag globals

A global variable is treated as a feature flag if its name matches the pattern:

g_feature_ | _enabled$ | _flag$ | kEnable | FEATURE_ | _ENABLED | FLAGS_
// Examples: g_feature_zlib, kEnableNewParser, FLAGS_use_compression

Step 2: Prove the flag is zero (three sub-paths)

Sub-pathConditionHow
Fast path Branch condition is already a ConstantInt A prior globalopt pass already folded the constant. Direct dyn_cast<ConstantInt> check.
Static path Global has internal linkage, zero initialiser, and no stores anywhere isConstantZeroGlobal(): checks linkage + initialiser + scans all users for StoreInst. Needs no prior opt passes.
Slow path Other cases LazyValueInfo::getConstant() — LLVM's backwards dataflow analysis that can prove a value is constant given branch constraints upstream.

Phase 3 — Interprocedural Dead Functions confidence 0.60

What it finds: Entire functions that are never called from anywhere reachable from the program entry point.

Algorithm: BFS from live roots

  1. Start with a live set = main() + all functions with external linkage (exported symbols)
  2. Use LLVM's CallGraph to expand: for each live function, add all its callees to the live set
  3. Any function in the module but not in the live set is dead
Why only 0.60? Indirect calls (via function pointers) are conservatively ignored. A function reachable only via a function pointer would be a false positive. Lower confidence signals "verify before deleting."

Pass Registration (how the plugin wires up)

// plugin.cpp — how LLVM finds and loads our pass
llvmGetPassPluginInfo() {
    return {LLVM_PLUGIN_API_VERSION, "DeadFeaturePass", LLVM_VERSION_STRING,
            [](PassBuilder &PB) {
                PB.registerPipelineParsingCallback(
                    [](StringRef name, ModulePassManager &MPM, ...) {
                        if (name == "dead-feature") {
                            MPM.addPass(DeadFeaturePass(outputPath));
                            return true;
                        }
                        return false;
                    });
            }};
}
Section 5 · Component 3

Report Generator

The report generator is a Python package (src/reporter/) that takes the raw IR findings and the config manifest and produces the final report.json used by the GUI.

Four sub-modules

merge.py

Joins IR findings with config data by matching source file basenames. Deduplicates findings from multiple bitcode files (per-TU and whole-program) by (function, source_file, start_line). Adds a human-readable feature_name inferred from function/BB names.

score.py

Applies the confidence scoring table. Already set by the IR pass, but score.py can override or adjust based on config correlation (e.g. a finding in a source file that's always compiled = lower confidence).

render.py

Writes the final report.json and a human-readable report.txt summary. The JSON schema mirrors the TypeScript types in the frontend exactly.

binary_size.py

Measures how many bytes of compiled code could be removed. Uses llc -filetype=obj to compile bitcode to an object file, then llvm-nm --print-size to read per-symbol sizes.

Confidence Score Table

Confidence is a float in [0.0, 1.0] indicating how certain the tool is that a finding is truly dead:

0.95
compile_time — structural IR property; no predecessors in CFG
0.85
runtime — flag proven zero by direct global inspection or LazyValueInfo
0.60
interprocedural — function unreachable by call-graph BFS (may have false positives via function pointers)
0.35
heuristic — name-match only, no dataflow proof
Confidence rangeMeaningRecommended action
≥ 0.8Provably dead under all enumerated configurationsSafe to remove in automated refactoring
0.5 – 0.79Likely dead; requires manual verificationReview before removing
< 0.5Possibly dead; flagged for awarenessInvestigate only

Binary Size Estimation

For whole-function dead findings (interprocedural), the reporter measures the exact compiled size of the dead symbol using llvm-nm --print-size. For block-level findings (compile_time / runtime), it estimates using estimated_lines × bytes_per_line, where bytes_per_line is calibrated against the measured whole-function symbols in the same run. The result lands in stats.removable_bytes.

A syntax highlighting library. Used in the Source Viewer to display C/C++ source code with coloured keywords, strings, and comments. Dead line ranges are overlaid in red on top of the highlighted code.

Backend Technologies

FastAPI

A modern Python web framework. Automatically generates OpenAPI docs from type annotations. Used for all REST endpoints. Chosen for its speed (Starlette/ASGI) and async support needed for the SSE log stream.

uvicorn

An ASGI web server for Python, based on uvloop. Serves the FastAPI app. Launched by python -m gui; auto-starts the browser after binding the port.

Server-Sent Events (SSE)

A web standard for one-way real-time streaming from server to browser. Used for the live pipeline log: as opt processes each bitcode file, log lines are streamed to the GUI in real time without polling.

Path-traversal guard

The /source endpoint resolves the requested path and checks it is a prefix of --source-root before reading. Prevents a crafty user from reading /etc/passwd via the GUI.

Section 9

Key Design Decisions (Q&A Ready)

These are the decisions most likely to be asked about in a demo or review.

Q: Why use LLVM IR instead of analysing source code directly?

Source code is ambiguous — macros, includes, and preprocessor state make it hard to reason about. IR is fully resolved by the compiler: all types are explicit, all control flow is a CFG, and DWARF debug metadata still links every instruction back to the original source line. Analysing IR means we can use proven LLVM analyses (LazyValueInfo, CallGraph) instead of reimplementing them.

Q: Why require -O0 bitcode? Can't you use optimised code?

At -O1 and above, LLVM's simplifycfg pass deletes unreachable basic blocks before our pass can see them. The whole point of the tool is to report these blocks as dead so developers know about them — if the compiler silently deletes them, we learn nothing. -O0 preserves them.

Q: Why don't you need globalopt or constprop pre-passes?

The key insight is isConstantZeroGlobal(): if a global has internal linkage, a zero integer initialiser, and no StoreInst in its user list, it is provably zero — no dataflow analysis needed. This means compile_time and runtime phases can run together in the same -O0 pipeline without pre-passes that would delete the compile_time blocks.

Q: Why is interprocedural confidence only 0.60?

The call-graph BFS conservatively ignores indirect calls (function pointers). A function reachable only via a function pointer would be a false positive. The lower confidence score is an honest signal: verify this finding before removing the code.

Q: What is the source-file security guard in the GUI?

The /source endpoint calls Path(file).resolve() and checks that the resolved path starts with the configured source_root. Without this check, a crafted request could traverse to /etc/passwd or other sensitive files.

Q: How does the live log in the GUI work?

The pipeline runs as an asyncio background task. As opt finishes each bitcode file, the pipeline emits a log line to an asyncio.Queue. The GET /run/log endpoint is an SSE (Server-Sent Events) stream — the browser keeps the HTTP connection open and receives each line as it arrives, giving a real-time progress view.

Q: How do findings from multiple bitcode files avoid being counted twice?

reporter/merge.py deduplicates by the tuple (function_name, source_file, start_line). When the same dead region appears in both a per-TU bitcode and the merged whole-program bitcode, only the entry with the highest confidence is kept.

How to Run the Tool

Step 1: Build

# Build everything: LLVM pass + Python venv + React frontend
./build.sh

This runs CMake to compile DeadFeaturePass.so, creates a Python virtual environment, installs FastAPI/uvicorn, runs npm install, and runs vite build to bundle the frontend.

Step 2: Run a test case

# Run TC-06 (large demo) with the GUI — recommended for demos
./run.sh --testcase 06 --gui

# Run a specific test case without GUI
./run.sh --testcase 01

Step 3: Run on your own project

# 1. Compile your project to bitcode
clang -O0 -gline-tables-only -fno-discard-value-names \
      -emit-llvm -c src/myfile.cpp -o build/myfile.bc

# 2. Link bitcode files
llvm-link build/*.bc -o build/program.bc

# 3. Run the full pipeline + open GUI
python -m gui.backend   # opens Setup tab; fill in build_dir + source_root
